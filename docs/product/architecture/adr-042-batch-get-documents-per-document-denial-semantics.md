# ADR-042: `BatchGetDocuments` Denial Semantics Are Per-Document, Not Per-Call (Amends DISCUSS Resolution 5)

**Status**: Accepted
**Date**: 2026-08-30
**Feature**: `batch-get-documents`
**Amends**: `docs/feature/batch-get-documents/feature-delta.md` § Resolution 5 (DISCUSS's own draft resolution, flagged by the orchestrator for DESIGN reconsideration, not overridden lightly)

## Context

`handle_get_document` (`crates/embyr-server/src/grpc/handler.rs:588-717`) has an established, structural existence-non-leakage guarantee: when a collection has an access rule, `evaluate()` is called unconditionally (even for a non-existent document, against an empty field map), and a `Deny` outcome ALWAYS produces `Status::permission_denied` — the caller can never tell from that status alone whether the document exists with the wrong owner or does not exist at all.

DISCUSS's own draft Resolution 5 proposed extending this guarantee to `BatchGetDocuments` at the *call* level: any single denied document in a batch rejects the entire request as `Status::permission_denied`, mirroring `GetDocument`'s per-call denial mechanically.

The orchestrator flagged a moderately-confident concern after DISCUSS's handoff: real Firestore's own `BatchGetDocuments`/`getAll()` behavior under Security Rules denial is, to the orchestrator's recollection, evaluated **per document** — a client batching several refs where one is denied still receives results for the others. If true, DISCUSS's whole-batch-abort choice would silently drop every OTHER legitimately-accessible document in the same call, directly undermining this feature's own named core use case (resolving several foreign-key-style references gathered from a prior query, where not every reference being accessible is an ordinary, expected outcome).

This ADR resolves that question deliberately, not by default to whichever reading "sounds safer."

## Decision

**Denial is evaluated and resolved per requested document, not per call.** A collection's `evaluate()` returning `Deny` for a specific requested document causes that ONE document to resolve as a `missing` result in the response stream — identical in shape to a document that does not exist. It does **not** abort the batch; every other requested document (in the same or a different collection) resolves normally per its own independent `evaluate()` outcome. `BatchGetDocuments` never returns `Status::permission_denied` for the call as a whole on account of one denied item.

### Decision drivers

1. **Wire-shape constraint (structural, not stylistic).** `BatchGetDocumentsResponse` (`firestore.proto:139-153`, already fully vendored, confirmed by direct read) carries `oneof result { Document found = 1; string missing = 2; }` — there is no third "denied"/error variant on the wire. Real Firestore SDK clients only know how to parse these two shapes for a data message. Inventing a new oneof arm to carry a distinguishable "denied" signal would break wire compatibility with real client libraries — directly contradicting JOB-01's own core value proposition (wire-identical SDK behavior). Whatever denial signal this feature emits per item MUST already be one of `found` or `missing`.
2. **Best-available knowledge of real Firestore (moderate confidence, stated explicitly, not disguised as certainty).** This architect's own recollection, consistent with the orchestrator's own independently-stated moderate confidence, is that Security Rules evaluation for `BatchGetDocuments`/`getAll()`-style batched reads is fundamentally per-document — each requested reference is independently rule-evaluated; a denial on one does not abort delivery of the others. This is flagged as a residual, non-blocking DELIVER-time verification candidate (same treatment this codebase already gives ADR-038's own field-number-verification residual for `aggregation-queries`), not as a blocking open question.
3. **Non-leakage is preserved at the per-item level, expressed through the wire shape available to a streaming RPC — and the rejected alternative (whole-batch abort) would leak strictly more than either option, not less.** Mapping `Deny` to `missing` makes a denied document literally indistinguishable on the wire from a genuinely absent one for that specific item — isomorphic to, not a strengthening of, `GetDocument`'s own guarantee (which already makes `Deny` indistinguishable from "does not exist" at the single-document level; batch simply applies the identical property per item instead of per call, because the per-item wire shape has no separate status channel to carry a distinct "denied" signal in the first place). What batch-level abort (the rejected alternative) WOULD add is a coarser but still real, additional leak on top of that: "at least one of my N requested refs has an access problem" — a fact the per-document `missing` design never reveals — while ALSO blocking legitimate access to the other N-1 documents. That is worse than the chosen design on both the security axis (an extra distinguishable signal) and the availability axis, for zero offsetting benefit.
4. **Core use case alignment.** The feature's own named value proposition (DISCUSS Resolution 2, User Story elevator pitch) is resolving a batch of document references gathered from a prior query or a stored list — where some references having gone stale, been deleted, or being inaccessible is an ordinary, expected outcome, not an exceptional one. Whole-batch abort actively defeats this use case for the caller's OTHER, perfectly legitimate documents in the same call.
5. **Uniformity is preserved at the property level, not forced at the wire-status level.** `GetDocument`'s guarantee — "a `Deny` outcome never reveals whether the document exists" — holds identically inside `BatchGetDocuments`'s own per-document evaluation. The two RPCs necessarily diverge in HOW that guarantee is communicated (a real gRPC `Status` for a unary call vs. a wire-legal `missing` value for one item in a stream with no per-item status channel) because their WIRE SHAPES differ, not because this design is inconsistent. Forcing identical status-code-level behavior onto a fundamentally different wire shape would require inventing a wire-incompatible third message shape (rejected by driver 1) or aborting legitimate access (rejected by drivers 3-4).

### Alternatives considered

**A. Whole-batch abort on first `Deny` (DISCUSS's own original Resolution 5).** Rejected: undermines the feature's own core use case (driver 4); on the best available (moderately-confident) knowledge of real Firestore, likely diverges from real SDK client expectations (driver 2); leaks a coarser but real signal while providing no additional security benefit over the chosen option (driver 3).

**B. Stream `found`/`missing` for every resolvable item, then terminate the stream with a terminal `Status::permission_denied` once a denied item is reached (partial-success-then-error).** Rejected: still leaks a distinguishable terminal condition (a denial-triggered stream termination is observably different from a clean end-of-stream) — worse non-leakage than Option C for no additional benefit; behavior becomes dependent on iteration order over `documents`, which a caller could probe by reordering requests across repeated calls; and it requires either buffering the whole result set to guarantee non-denied items are flushed first, or accepting non-deterministic partial delivery, both meaningfully more complex than Option C's single per-item branch for no offsetting benefit.

**C. Per-document, `Deny` -> `missing` (chosen).** Zero proto changes, uses only wire-legal values, strongest available non-leakage property, fully serves the batch's own core use case, and is the simplest implementation (a single branch inside the existing per-document loop, mirroring `handle_get_document`'s own `evaluate()` call site with a different terminal mapping for the `Deny` arm).

## Consequences

**Positive**: real-Firestore-client compatible on best-available knowledge; the feature's own core use case (partial-batch resolution) is fully served; existence-non-leakage is preserved at the per-item level (isomorphic to `GetDocument`'s own single-document guarantee), and the rejected whole-batch-abort alternative's additional leak is avoided; zero proto changes; minimal implementation complexity — the `Deny` arm becomes a loop-local `missing` push instead of an early `Err` return.

**Negative**: a caller can no longer distinguish, from `BatchGetDocuments` alone, "this specific document is denied" from "this specific document does not exist" — by design (driver 3), but named explicitly as a real behavior difference from a caller's perspective. A caller who needs that finer-grained diagnostic signal for one specific document can still call `GetDocument` directly for it, which is completely unchanged by this feature and still returns a real `Status::permission_denied` for that case.

**Negative**: `GetDocument` and `BatchGetDocuments` now handle the identical `Deny` outcome differently at the wire-status level (one is a call-level `Status::permission_denied`, the other is a per-item `missing` value) — an intentional, structurally-forced divergence (driver 5), documented here so it is never mistaken for an inconsistency or a bug during DELIVER or future maintenance.

**Residual, non-blocking**: real Firestore's exact `BatchGetDocuments`-under-Security-Rules-denial behavior is not verified against a live system or network-sourced documentation in this sandbox — recommended as a lightweight DELIVER-time or follow-up confirmation, not a blocker (same treatment as ADR-038's own field-number-verification residual).
